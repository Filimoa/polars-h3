# H3 core optimization results — 2026-11-26

This pass vendors **h3o 0.11.0** and speeds up its core algorithms on top of the already-optimized Polars wrappers. In the large matched run, coordinate indexing improves **1.69×**, directed-edge creation **2.83×**, and all-vertex generation **4.46×**. Public Python APIs, dtypes, null/invalid handling, list order and pristine-Rust results are preserved.

The baseline is the completed wrapper implementation at `fe34e2f`, not the original slow implementation. The [wrapper report](2026-11-25-wrapper-pass2.md) retains the earlier gains; do not multiply ratios from different workloads or runs. The core work is in [PR #29](https://github.com/Filimoa/polars-h3/pull/29), stacked on wrapper PR #28.

All **53 internal workloads** pass at row caps of 1,000, 16,384, 100,000 and 5,000,000 with eight threads, and at 100,000 with one thread. Small operations often spend more time in dispatch and scheduling than in H3; their sub-millisecond timings vary, and no speedup is claimed for every helper.

Ten-sample follow-ups investigated apparent slowdowns. String compaction measured 78.70 ms baseline versus 79.35 ms candidate, with overlapping ranges; 128-row large-set compaction measured 0.406 versus 0.422 ms, also overlapping. Integer compaction was essentially unchanged at 48.84 versus 48.92 ms. Repeated 100,000-row child/edge-list probes likewise did not establish a material regression. The core disk-compaction microbenchmark improves about 11%, but that does not translate into a reliable general Python compaction speedup.

The final neighbor/owner cache improves all-vertex expansion another **1.30×** versus the intermediate vendored build (88.39 → 68.05 ms for four million rows). In the same matched follow-up, single-vertex lookup is **2.4% slower** than that intermediate build (26.91 → 27.57 ms for five million rows). This small tradeoff is retained for the larger all-vertex gain; both remain substantially faster than the wrapper-only baseline.

## What changed and where time remains

- Packed digit rotations and paired neighbor transitions replace repeated per-digit work. Ordinary neighbor moves stay on a small inline path; base-cell and pentagon corrections retain the general path. Directed-edge lookup checks one candidate direction for ordinary same-base cells. Resolution-zero moves have their own exact transition.
- Coordinate conversion uses exact integer aperture-seven rounding, pairs of refinement steps and cached face tangent bases. A direct gnomonic projection avoids redundant intermediate angles, with the original arithmetic retained near face centers and cell boundaries. No blanket fast-math, reduced precision or CPU-specific build flags are enabled; no_std retains the original projection path.
- Vertex enumeration reuses origin orientation, neighboring cells and owner orientation. Single-vertex calls omit neighbor caches through compile-time specialization. Cell validation preserves error precedence while simplifying valid headers and digit checks.
- Polygon coverage streams generations instead of cloning each layer and avoids redundant hash-set writes. Compaction skips ancestors that cannot form a complete subtree from the current sorted cell.

Five-second CPU samples of the combined build were collected separately from timings. Remaining indexing work is predominantly inside `LatLng::to_cell`; disks spend time in neighbor transitions and their iterator. Polygon work is spread across projection, containment, traversal and allocation. Cell area is dominated by `atan2` and boundary projection. The vertex profile directly motivated the final neighbor cache. Inlining and waiting stacks make these hotspot evidence, not exact percentages or mathematical speed ceilings.

A closest-face map-before-reduce experiment had no worthwhile gain and was reverted. A rotation-level resolution-zero shortcut was replaced by the measured base-cell transition. Polygon streaming was compared with batching under the same deduplication rule. Cheap hierarchy helpers already mostly manipulate bits or write output buffers, and area calculations already reuse adjacent trigonometric values. Further gains may require specialized workloads, different algorithms or different numerical contracts; this pass makes no claim of mathematical optimality.

## Validation

- **469 Python tests** pass using the rebuilt release extension. **790 exact saved-plugin comparisons** cover all 53 workloads in native/signed/string representations, empty inputs, invalid values, nulls, uneven chunks and sliced validity offsets.
- Preserved upstream suite: **119 unit tests, 924 integration tests and 95 doctests** pass. Formatting, vendor all-target Clippy, root Clippy, Ruff, Python type checks and no_std checks pass.
- The standalone laboratory pins pristine crates.io h3o 0.11.0. Nine tests include **16 million coordinate/resolution pairs**, exhaustive low-resolution cells, all-resolution pentagons and neighbors, boundary-adjacent floating values, exact floating bits, vertices/edges, malformed-index errors, ordered polygon annotations and compaction/error mutations.
- The seeded final-source differential fuzzer completes **6,197,274 inputs in 301 seconds without a mismatch**, including compaction checks. All 16 inherited upstream fuzz targets compile; 15 pass short smoke campaigns. The coordinate target still finds inherited extreme-coordinate disagreements with C H3, confirmed against pristine Rust. The existing tiny-cell area-tolerance finding also remains documented. These assertions are not suppressed and scheduled C-reference fuzzing can fail on them. See [vendored provenance](../../vendor/h3o/UPSTREAM.md).
- The source-distribution verifier compares every packaged extension/vendor Rust file byte-for-byte, forces both packages to compile from the extracted source, and verifies h3o’s BSD license in the wheel. This avoids stale Cargo artifacts caused by normalized archive timestamps.

Cross-library DuckDB validation checks every output outside timing, normalizing only unordered list order and using relative tolerance 1e-7 / absolute tolerance 1e-9 for floats. Exact regression checks against pristine Rust and the saved Python plugin use stricter equality. Known cross-library Boolean null conventions are not silently normalized; the main DuckDB matrix uses non-null inputs.

Python H3 callbacks and bounded h3-py/h3pandas comparisons remain available through the [benchmark guide](../README.md). This pass does not replace their prior evidence with new headline claims. Raw data is kept locally; no benchmark attachments are uploaded.

Choose fresh output paths: runners refuse to overwrite evidence.
